# Contributing guide

This guide summarizes how to work in `mentorapredict-services` and `mentorapredict-clients` (the rules are the same in both).

**Language:** commit messages, pull request titles and branch descriptions are written **in English**.

## 1. Workflow at a glance

1. Start from an up-to-date `dev`.
2. Create one work branch per Jira task.
3. Make small commits that follow Conventional Commits: each subtask is one or more commits.
4. Open a pull request (PR) to `dev` and fill in the template.
5. Review your own PR and merge it with a merge commit.
6. Promotion `dev` → `qa` → `main` is done by PR; the step to `main` is approved by the instructor.

## 2. Branches

Permanent branches: `dev` (development and integration), `qa` (release candidate) and `main` (production). They are protected: nobody pushes directly.

Work branches start from `dev`. There is **one branch and one pull request to `dev` per Jira task**; its subtasks do not need their own branch or pull request: their commits go in the branch of the task. A branch uses this format:

```text
<type>/<JIRA>-<cod>-<description>
```

- `type`: `feat`, `fix`, `chore`, `docs` or `ci`.
- `JIRA`: the key of the Jira task, not of a subtask (for example `MPC-123`), when there is one. **It is what links the branch and the PR to the task.**
- `cod`: code of the service or area (`grd`, `idn`, `infra`, `web`...).
- `description`: in English, lowercase and hyphenated.

Examples:

```text
feat/MPC-123-grd-quarter-closing
fix/MPC-124-att-late-justification
chore/MPC-80-infra-base-structure
docs/MPC-86-docs-readme-contributing-guide
```

```bash
git checkout dev
git pull
git checkout -b feat/MPC-123-grd-quarter-closing
```

The branch `release/<cod>-<MAJOR.MINOR>` exists only to fix an already published version.

## 3. Commits

Conventional Commits format:

```text
type(scope): description

Optional body explaining the change and its purpose.

Refs: MPC-501
```

Separate the header, body and footer with blank lines. The body and `Refs:` footer
are optional; when useful, use the body to explain the change or its motivation,
and use `Refs:` to identify the relevant Jira subtask. Write all parts in English.

- **type:** `feat`, `fix`, `hotfix`, `perf`, `refactor`, `style`, `test`, `docs`, `build`, `ci`, `chore` or `revert`.
- **scope:** optional and free, in lowercase. It is recommended to use the service code (`grd`, `idn`...) or an area such as `web`, `mobile`, `desktop`, `contracts`, `platform`, `infra`, `gitops`, `docs` or `release`.
- **description:** in English, imperative mood and no final period. The whole header (`type(scope): description`) has at most 100 characters; what does not fit goes in the body.
- The body, if any, is also in English and has no line length limit.
- The Jira key does **not** go in the header: the branch name already has it.
- **Subtasks:** a subtask is one commit or several, as needed. **Optional but recommended:** reference the subtask in each of them with a `Refs:` footer as the last line of the message, after a blank line: `Refs: MPC-501`. So several commits can have the same reference (a commit that covers several subtasks lists them separated by commas). `commitlint` does not require this footer: a commit without it is valid.

Examples:

```text
feat(grd): calculate the weighted average of the quarter
fix(att): allow late justification
chore(infra): create base monorepo structure
docs(docs): write README and contributing guide
```

Two commits of the same subtask (each `-m` is a separate paragraph):

```bash
git commit -m "feat(grd): calculate the weighted average of the quarter" -m "Refs: MPC-501"
git commit -m "test(grd): cover the weighted average with missing grades" -m "Refs: MPC-501"
```

Example with a body and a subtask reference:

```text
feat(infra): add the QA network

- Create the VPC and subnets across two availability zones.
- Configure routing, NAT and gateway endpoints.

Refs: MPC-189
```

Because every merge is a merge commit, all the commits of the branch are kept. So **every commit** must follow the format, not only the PR title: the `commitlint` check of each pull request validates all of them and the title. Merge commits and the revert commits generated by GitHub are not validated.

A breaking change adds `!` after the scope (`feat(grd)!: ...`) and `BREAKING CHANGE:` in the commit footer.

## 4. Pull requests

- **Title:** in English and with the same format as a commit: `type(scope): description`. The titles feed the automatic release notes.
- **Target:** `dev`. Promotions go from `dev` to `qa` and from `qa` to `main`.
- **Scope:** one PR to `dev` per Jira task, with all its subtasks. The key of the task goes in the branch name and in "Closes:", and "Changes" lists what each subtask changed. If only some subtasks are going to be merged, say which ones and do not close the task.
- **Changes:** every PR explains the changes that were applied, in "Changes". Use bullet lists, subheadings, paragraphs or a mix; the title or the list of commits is not enough.
- **Template:** fill in every section that applies. Delete, with their heading, the sections that do not apply or have nothing to say: never leave a section with only "N/A" or "None". In the sections with options (Module, Type of change, Impact) keep only the selected option and delete the rest.
- **Task:** write the key in "Closes: MPC-NN".
- **Commits table:** in a work PR, fill in "Commits Included" with one row per commit: short ID, title, author and Jira subtask or task. The key is the one in the `Refs:` footer of the commit or, without it, the key of the branch. This command, run in your branch, prints the rows; the last column stays empty for commits without `Refs:`, so write the key of the task there:

  ```bash
  git fetch origin
  git log --reverse --no-merges --format="| %h | %s | %an | %(trailers:key=Refs,valueonly,separator=%x2C ) |" origin/dev..HEAD
  ```
- **Public repository:** do not push secrets, AWS account IDs or real student data.

## 5. Review and merge

| Target | Approvals | Who merges |
| --- | --- | --- |
| `dev` | 0 | The author, after reviewing their own code |
| `qa` | 0 | The author |
| `main` | 1, from the course instructor | The author, once approved |

- There is no cross review and no first-review deadline between developers: **each person reviews their own code**, guided by the recommendations below.
- Merge method: always merge commit. No squash and no rebase, so `dev`, `qa` and `main` do not diverge.
- If a check fails (for example `commitlint`), do not merge.

### Self-review recommendations (DOC-CAL-06)

These are recommendations, not a form: each author applies the ones that fit the change. They are not copied into the pull request.

- **Code:** read the full diff yourself; check that the commits follow Conventional Commits in English.
- **Tests:** add unit tests of the domain and, if the change touches another service, integration or contract tests; all should pass.
- **Contract:** if a route or event changes, update the OpenAPI or event contract.
- **Security:** routes require session and role and have a negative test; there are no secrets, AWS account IDs or real data.
- **Environment:** the change works with the single startup command and the seeds.
- **Acceptance:** check the acceptance criterion of the requirement (`RF-...`).
- **Documentation:** if the behavior changes, update the document that owns it.

## 6. Promotion between environments

1. PR from `dev` to `qa`, titled `chore(release): promote dev to qa`.
2. PR from `qa` to `main`, titled `chore(release): promote qa to main`; the instructor approves it.
3. In both PRs, fill in the table "PRs Included From Development or QA" with the PRs merged since the last promotion.

The title of a promotion is **always the same**, without a version number: `chore(release)` does not publish by itself, and the version is calculated from the commits being promoted (see section 8). What changes in each promotion is the **body**: the Jira tasks that enter, the table of PRs merged since the last promotion, the summary of changes and, if there are any, the breaking changes. A breaking change is written in the body and in the commits with `!`, never in the title.

## 7. If something goes wrong

- **The `commitlint` check fails:** the check is required in `dev`, `qa` and `main`, so the PR cannot be merged, not even by administrators, until it passes.
  - *The PR title is wrong:* edit the title in the PR. The check runs again by itself.
  - *A commit message is wrong:* rewrite it in your work branch (it is not protected) with `git commit --amend` for the last commit or `git rebase -i` for older ones, and push with `git push --force-with-lease`. It must be fixed in the branch because, with merge commits, every commit stays in the history.
  - *A promotion PR (`dev` to `qa` or `qa` to `main`) fails:* it should not, because each commit was already checked when it entered `dev`. If it happens, ask the owner of your module; history of `dev`, `qa` and `main` is never rewritten.
- **You merged something wrong:** do not rewrite history. Open a revert PR with `git revert`, titled `revert: ...`.
- **Your branch is out of date:** bring `dev` into your branch with `git merge origin/dev` and solve the conflicts before opening the PR.
- **Doubts about a rule:** ask the owner of your module.

## 8. Tags and releases

Tags and releases are created automatically when a PR is merged into `qa` or `main`; you do not create them by hand.

- A merge into `qa` creates a release candidate tag `vX.Y.Z-rc.N` (pre-release).
- A merge into `main` creates the stable tag `vX.Y.Z` and its GitHub Release with generated notes.
- The version comes from your commits: `feat` raises the minor number; `fix`, `hotfix` and `perf` raise the patch number; a `!` after the type or a `BREAKING CHANGE:` footer is a breaking change. Commits of type `docs`, `style`, `refactor`, `test`, `build`, `ci` and `chore` do not create a release.
